Test your whole workflow: the priority_check Python package

What it is. The Auditor's Python package (Python 3.9+, standard library only). priority_check workflow runs your own multi-agent workflow through a small adapter, with each of two opposite priorities, without a priority, and with the priority given directly or restated to the decision step, in both option orders, in fresh executions. It records what every agent received and decided, and checks the runs' integrity. priority_check compare compares two runs after you change something. (priority_check chain runs our fixed six-handoff reference workflow instead, if you have no adapter yet.)

Status: public beta 0.1.0b1. Python 3.9+, no dependencies. Download it here (it is not on a package index): source archive with examples and tests (.tar.gz) · wheel (.whl, package only). Licence: MIT (the archive's LICENSE file). Offline? Install the wheel (pip install priority_check-0.1.0b1-py3-none-any.whl) and run the quickstart from the extracted source archive, which holds the examples; pip install . fetches setuptools.

Quickstart: run the example workflow (offline, no API key, about 5 minutes)

tar xzf priority_check-0.1.0b1.tar.gz && cd priority_check-0.1.0b1
python3 -m venv .venv && . .venv/bin/activate && pip install .
PYTHONPATH=examples/minimal_workflow python -m priority_check workflow --scenario examples/chain_scenario.example.json \
    --adapter my_adapter:MyAdapter --runs 2 --orders both --out results_v1
PYTHONPATH=examples/minimal_workflow python -m priority_check workflow --scenario examples/chain_scenario.example.json \
    --adapter my_adapter:MyAdapter --runs 2 --orders both --config '{"forward_priority": true}' --out results_v2
python -m priority_check compare --baseline results_v1 --candidate results_v2

The example has a deliberate flaw (the researcher's prompt is built from the intake brief with the priority cut off), so the first run shows workflow 0 of 4 pairs and the fixed run 4 of 4; compare reports CONFIGURATION CHANGE (exit code 3; 0 means the same configuration, 5 not a valid comparison). It uses a deterministic fake model: this shows the tool working, not anything about a real model. Open each run's summary.json and records.jsonl on Inspect to see what every agent received (read in your browser, not uploaded); report.md has the counts. The archive's README walks through each step.

The loop

  1. Map what each agent should receive, and save the scenario file: Workflow Map.
  2. Connect your workflow with an adapter (contract below; a complete example is in the package at examples/minimal_workflow/my_adapter.py).
  3. Run it: python3 -m priority_check workflow --scenario my.scenario.json --adapter my_adapter:MyAdapter --runs 2 --orders both --out results_v1
  4. Inspect the result: open summary.json and records.jsonl in Inspect and compare to see the verdict and what each agent received.
  5. Change your workflow (or pass --config '{"...": ...}'), run again into results_v2, and compare: python3 -m priority_check compare --baseline results_v1 --candidate results_v2, or open both on the Inspect page.

With a real model, every call is billed to your own key: the run then requires --i-accept-costs and --max-executions equal to the planned number. The example uses an offline fake model; its output is not evidence about any model.

The adapter contract

  • describe() returns name, version, fake (true/false), provider, models (exact pinned model ids), settings, agents, priority_entry, and supports: {"direct": bool, "restored": bool}.
  • run(request) runs the whole workflow once, in a fresh context. request has task, option_a, option_b, priority (null in the no-priority control), execution_id, config. Return final_text (first line FIRST CHOICE: A, B or UNCLEAR; anything else counts as INVALID), trace, models_served, and decision_input (what the decision step received, needed for the restated check).
  • Optional: decide_direct(request), the decision step alone given the priority; decide_restored(request, decision_input), the same upstream input plus the priority restated.

The trace format (apa-trace/1)

One entry per agent call, with the exact messages sent to the model. The Map page can also open a trace saved from Inspect.

{"format": "apa-trace/1",
 "agents": [
  {"id": "researcher", "role": "research", "model": "your-pinned-model-id",
   "request_messages": [{"role": "user", "content": "the exact text sent"}],
   "request_complete": true,
   "state_visible": null, "state_complete": true,
   "output": "what it returned"}]}

Steps that call no model (a filter, a compressor, a tool): record them too, with their input as one message, for example "request_messages": [{"role": "input", "content": "the exact text it received"}], "model": null and their output. Otherwise their input is reported as "not captured", and text they drop or pass on can't be followed.

Other trace formats (for example LangSmith or OpenTelemetry exports) are not imported yet: convert them to this shape.
